# 订单分析 Agent 第一版实验报告

实验日期：2026 年 10 月 14 日

## 目标与范围

本项目实现一个能够根据用户任务调用订单查询工具、比较月消费额并输出结构化答案的 Agent。

重点验证工具调用、参数校验、失败处理、重复调用保护与自动评测。使用练习数据，不涉及真实业务生产部署。

## 系统设计

模型使用 DeepSeek 官方 API 的 deepseek-flash。程序通过 Python 实现执行循环，数据库使用 MySQL，驱动使用 PyMySQL。

执行过程：

1\. 接收用户任务。

2\. 将任务、工具说明和历史结果发送给模型。

3\. 模型提出工具调用。

4\. 程序检查工具白名单与参数，执行只读查询。

5\. 将工具结果关联调用 ID，反馈给模型。

6\. 模型继续调用工具或输出最终 JSON。

程序设置最多六轮模型请求、四次工具调用。同一任务内，相同工具与参数最多尝试一次，被拦截的请求仍计入调用预算。

## 业务与评分口径

跨月比较取两个查询结果的用户并集。

查询成功且数据完整时，某用户未出现在当月结果中，按没有订单处理，消费额补零。查询失败时金额未知，不允许补零。

变化金额等于后一个月减去前一个月。下降金额并列时，选择用户编号最小的用户；没有下降时返回 null。

评测分别检查执行过程和最终答案，包括工具参数、所需数据、JSON 字段、用户集合、金额变化及下降用户。

业务状态包括 completed、unable_to_complete 和 needs_clarification。程序正常结束与业务任务完成分别判断。

## 关键发现

### 空数据与失败必须区分

十月查询成功但返回空列表时，模型正确计算九月用户的消费下降。

十月查询失败时，模型说明无法完成比较，没有将未知金额当作零。

### 输入澄清影响效率

较早一次非法月份实验中，模型先查询有效月份，再请求澄清。后续三次实验均直接澄清，没有工具调用。

由于不同阶段的条件未完全对齐，不能将这一变化归因于某项修改。

### 工具保护需要由程序实现

重复调用集成测试使用脚本化模型，确定性地产生相同参数请求。第二次请求被拦截，执行入口只调用一次，拦截结果正确反馈给模型。

该结果证明控制逻辑有效，不证明真实模型收到拦截后总能正确调整。

## 限制

- 样本量小，任务主要围绕固定两个月的订单比较。

- 当前任务用于开发，没有独立保留测试集。

- 部分场景仅运行一次。

- 模型输出格式主要依赖提示词约束，运行时未统一执行完整业务校验。

- 澄清与失败原因的语义仍需人工判断。

- 重复调用保护目前也阻止失败后的相同查询，尚未实现合理重试。

- 部分实验使用注入数据，不验证真实数据库故障恢复。

- 发布整理时补跑评分器错误样本验证，7/7通过，详见release_validation.md。

- 尚未在全新机器验证安装与运行说明。

- 本项目没有进行固定工作流与 Agent 的效果对比，不能证明 Agent 是该任务的最优方案。

## 第一版结论

项目已形成模型决策、工具执行、结果反馈与自动评分的完整学习链路，并验证若干正常、异常和边界场景。

现有结果支持将其作为可演示的入门项目。它们不足以证明生产环境可靠性，也不应表述为“Agent 成功率100%”。

第一版在此冻结功能。后续改进另行设定目标和实验范围。
