# 订单分析 Agent：项目与面试详细问答

本文针对本仓库的实际实现。每题包括答案、项目落点和表达边界，未实现的功能明确列为后续方案。不要把建议当作已完成成果。

## 1. 请介绍这个项目

这是一个 Python 实现的订单分析 Agent。用户用自然语言提出跨月消费比较任务，模型决定查询哪些年月，程序执行只读 MySQL 查询，将结果反馈给模型，最后输出 JSON。工具校验、调用预算与重复保护由程序实现，而不是只依赖提示词。

评测分成两层：执行层检查工具名、参数、查询结果和调用次数；结果层检查用户并集、金额变化、下降用户及业务状态。真实数据库实验验证接口链路，注入实验覆盖失败与空数据，模拟模型集成测试验证重复保护。

一分钟表达：我实现了一个模型决策—工具执行—结果反馈的最小闭环，并围绕正常、澄清、非法输入及数据异常设计规则评测。重点是可验证性，不是复杂框架。现有样本少，结果仅限开发任务。

## 2. 固定程序也能做，为什么使用 Agent？

固定两个月查询与差值计算完全可以用确定程序完成，而且通常更便宜、稳定。这个学习项目选择 Agent，是为了练习自然语言任务解析、动态工具选择、执行反馈和异常解释。

增加的能力是模型根据用户输入决定年月与下一步；增加的成本是模型请求、延迟、格式错误和决策不确定性。当前没有对照实验，不能证明 Agent 在此任务优于固定工作流。

生产方案可以用模型解析需求、程序做金额计算，只有路径确实不确定时才开放更多自主决策。选择依据是任务需求与实验收益，而不是 Agent 标签。

## 3. Agent、工作流与 RAG 有什么关系？

工作流的路径主要由代码规定，可以包含模型、条件分支和循环。Agent 将部分行动选择交给模型，根据执行结果决定下一步。二者是连续谱，可组合使用。

RAG 是检索知识再生成回答的机制，可成为 Agent 的一个工具。此项目主要查询结构化订单，因此没有实现文档检索。不能声称做了 RAG，也不需要为了名称加上向量库。

## 4. 模型调用工具时，究竟是谁执行？

模型返回工具名称、JSON 参数与调用 ID。Python 程序检查名称白名单和参数结构，调用数据库函数，将结果放进 role=tool 的消息，用 tool_call_id 关联原请求，再发送下一轮模型请求。

模型没有直接访问数据库的能力。它提出行动，执行层掌握权限。必须保留模型的工具调用消息与所有对应结果，否则对话协议可能不完整。同一轮可有多个调用，本实现按顺序执行。

## 5. 为什么需要两层参数校验？

工具 Schema 帮助模型理解参数，但不是执行授权。分派层检查 JSON 对象、必需字段、额外字段及工具名；业务函数检查整数类型、月份范围与年份范围。直接调用工具函数时仍能获得保护。

Python 中 bool 是 int 的子类，因此 type(value) is int 用于明确拒绝 True。不能把字符串“9”静默转换而不说明接口约定。异常输入在连接数据库之前返回 INVALID_ARGUMENT。

## 6. 如何防止 SQL 注入？

工具执行固定 SQL，通过 cursor.execute(sql, (start, end)) 绑定值。输入不会通过 f-string 拼接为可执行 SQL。只读账号仅有练习表 SELECT 权限，用权限层限制写操作。

参数化主要保护数据值，不能拿占位符任意替换表名、列名。若未来允许动态标识符，应使用明确白名单。本项目不接受模型生成的任意 SQL，也没有实现“任意SQL安全执行器”。

## 7. 为什么时间筛选采用左闭右开？

使用 created_at >= 月初 AND created_at < 下月月初，能够覆盖整个月，不依赖最后一秒的精度。12月结束边界要进入下一年。相比在列上调用 YEAR/MONTH，范围条件更便于普通时间索引参与查询，但是否使用要看执行计划和数据分布。

练习列为 DATETIME，没有自动处理业务时区。真实系统应约定存储与查询时区，并先将业务月边界转换到存储口径。索引不是必然最优，不能仅凭存在索引就声称优化成功。

## 8. 为什么金额用 DECIMAL，而不是 float？

十进制金额用 MySQL DECIMAL 保存，避免二进制浮点表达造成金额误差。驱动返回 Decimal，工具转成两位小数字符串方便 JSON 序列化。参考答案计算使用 Python Decimal。

模型仍可能算错，所以评测器独立核对。未来可将计算移到确定性函数，让模型只做解释。严格格式评分与数值正确性应分开分析：“+50.00”可能数值正确但不符合当前字符串约定。

## 9. 为什么取用户并集？

只取交集会遗漏只在一个月出现的用户。并集保留离开用户与新增用户：当两个月查询均成功且结果完整，缺失用户按本项目约定补零，再求后月减前月。

缺失是否等于零是业务约定，不是普遍事实。分页未取完、权限过滤或数据晚到时，缺失可能是未知。因此补零的前提必须明确。

## 10. 空结果与查询失败怎么区分？

成功空结果为 ok=true、data=[]、error=null；失败为 ok=false、data=null、error=结构化错误。空结果表示没有匹配记录，失败表示没有可靠数据。

部分失败实验中九月成功、十月失败，正确输出 unable_to_complete，不能把十月金额补零。空月份实验十月成功为空，正确输出 completed 并计算下降。这组对照覆盖模型对结果语义的理解。

## 11. finished 为什么不等于 completed？

finished 是程序执行状态：模型返回了非空最终文本，没有继续调用工具。completed 是业务状态：模型声称完成任务。它也可以返回 needs_clarification 或 unable_to_complete。

当前程序退出0表示正常结束，评分器退出0表示通过其检查。要评价业务成功，需要校验答案与工具证据。运行时目前没有统一完整业务验证，这一点应作为局限而不是隐藏。

## 12. 如何避免 Agent 无限循环？

程序限制六轮模型请求、四次工具请求；执行前检查整批调用是否超预算；验证调用ID；重复保护记录工具与规范化参数，阻止同任务相同查询再次执行。

限制需要由代码落实，因为模型可能不遵守提示词。次数上限不等于精确总时间上限；网络超时也不等于完整任务截止时间。未来可加入总预算和取消机制，但目前未实现。

## 13. 重复调用怎么识别？有什么局限？

将参数解析为对象后按键排序序列化，以工具名加参数作为键，因此字段顺序不同也能识别。调用ID不同不影响识别。保护对象在每次 run_agent 内创建，不同任务不共享。

它保护的是“相同参数”，不是语义相同的所有请求；数据更新后同参数也可能有必要重查。当前失败也被记录，所以无法合理重试。该策略适用于本项目固定快照，不应直接推广到所有任务。

## 14. 合理重试应该怎样做？

先区分错误类型。无权限、参数非法通常不能靠原样重试解决；短暂网络故障可能可重试。设置最大尝试、总截止时间和退避，遵守服务限流信息。

只读查询容易控制副作用，但写入工具要有幂等键，避免一次请求超时后已经写入却再次执行。重试应与重复保护协调，并分别记录模型请求、执行尝试与成功次数。本仓库尚未实现此设计。

## 15. 怎么评测 Agent？

先明确任务成功标准，再同时观察结果、过程、可靠性与效率。结果看金额与最终业务状态；过程看工具/参数/所需数据；可靠性看失败处理、格式、越界；效率看工具次数、耗时与Token。

不是要求轨迹完全一致。九月先查或十月先查都有效。本项目“两个月各查一次”是当前固定场景的效率规则，未来允许恢复重试时应修改，不可当通用正确性标准。

## 16. 规则评分、人工评分与模型裁判怎么选？

金额、字段、最终状态等能计算的部分优先使用规则。澄清是否问到关键缺失信息、失败解释是否合理，当前仍人工检查。非空字符串不能证明语义正确。

模型裁判适合较开放任务，但需要明确rubric、人工校准，检查位置和冗长偏差，并记录裁判版本。不能让未经验证的模型裁判替代全部依据。本项目没有接入模型裁判。

## 17. 如何证明评分器本身可信？

正确记录应被接受；人为改错金额、下降用户、工具证据、JSON或失败时编造结果的副本应被拒绝。拒绝还应区分评分正常失败与评分器崩溃。原始记录保留不变。

参考答案独立从配置输入用Decimal重算，检查重复用户、月份与金额格式。独立计算仍共享业务规则，不是绝对真理；需要人工确认规则。本次发布会运行可用的评分器负例测试，并在发布验证中报告实际结果。

## 18. 任务集如何设计？

正常任务验证主路径；模糊任务验证澄清；非法月份验证输入边界；全失败与部分失败验证未知数据；空月份与两月为空验证空数据；无下降、并列及用户集合不同验证计算边界。

后续可加入自然表达变体、不同时间跨度、工具超时和不可信返回。但不要无限追加：先冻结范围，按错误分布扩展。当前配置属于开发集，不是独立保留测试集。

## 19. 为什么九次都通过还不能宣称100%成功率？

这是三个已知任务各运行三次，任务覆盖少，重复调用彼此不是九个独立新任务。提示词和评分规则也在这些任务上开发，存在适配开发集的问题。

可以说“该版本在三个开发任务的三次重复实验中通过当前检查”，不能推断真实业务成功率。正式比较应增加代表性任务、保留集和不确定性分析，区分任务间与任务内波动。

## 20. 修改后12/20变成14/20，怎么判断？

首先观察每个任务的配对变化：只修好两题与修好八题但退化六题，总数相同，回归风险不同。固定模型、工具、评分器、任务及预算，重复运行观察随机波动。

报告成功率差10个百分点、样本量和不确定性。根据设计考虑配对重采样或二元配对方法；重复同任务不能当全部独立样本。结合成本、延迟和严重错误决定采用，不能只看一次总数。

## 21. 如何记录成本与版本？

任务Token应汇总各轮 usage.total_tokens，不能拿最后一轮当任务总量。未收到响应的请求可能产生费用但不在本地统计中。金额成本还依赖当时价格、缓存和账户账单，不在本文给固定估算。

实验报告保存模型名称、源码哈希、任务、参数、评分版本与原始记录。还应固定数据库快照。别名背后的模型可能变化，仅记录名称不足以长期保证同版本。缓存与网络也影响延迟。

## 22. 如何做故障归因？

先检查配置与接口是否成功，再看模型是否选对工具/参数、工具是否返回可靠数据、计算与格式是否正确、评分器是否误判。分别标记模型决策失败、工具失败、运行异常、格式失败和规则失败。

本项目部分入口仍将不同失败合并为未通过，详细日志才支持归因。因此不能从一个退出码判断根因。保留所有失败记录，不只保存成功样本。

## 23. Python上下文管理器、mock为什么有用？

with 管理连接和游标生命周期，即使异常也退出上下文，减少资源泄漏。patch 临时替换引用点，退出后自动恢复。要替换 agent_demo.query_user_monthly_orders，因为执行函数从该模块查找名字。

模拟模型测试验证确定性控制逻辑；真实模型+模拟工具验证模型面对指定返回的行为；真实模型+真实数据库验证实际链路。三者覆盖不同，不可以互相冒充。

## 24. async/await能让此项目更快吗？

当前模型与数据库接口是同步阻塞。只给函数加async并不会非阻塞，可能卡住事件循环。独立月份查询可并发，依赖上一步结果的行动不能随意并发。

真正异步要用相应客户端或将阻塞I/O调度到受限线程，并处理连接安全、限流与取消。CPU计算可考虑进程或向量化。是否值得改应先测瓶颈，不把并发作为完成标准。

## 25. 如果改成生产服务，需要补什么？

补身份与权限、多用户隔离、输入及最终Schema校验、确定性金额计算、真实超时/重试/幂等、日志脱敏与访问控制、数据库快照/分页口径、监控告警和更完整测试。工具返回内容不能作为高优先级指令，外部文本注入要有信任边界。

部署还要配置管理、容量、成本与退化策略。这些是设计建议，当前仓库未实现，面试时不要说已经上线。

## 26. 简历和项目追问怎么说？

推荐表述：使用Python构建订单分析Agent，实现DeepSeek工具调用、MySQL只读查询、参数校验、调用预算与重复保护；构建正常、澄清及故障注入评测，校验结构化金额结果，保留执行记录与实验版本。

不要写“生产成功率100%”“支持任意SQL”“实现自动故障恢复”。可以引用有限实验次数，但必须交代开发集与注入数据。追问时先说真实完成的部分，再说下一步设计，不要将规模与框架名称替代理解。

## 三分钟复盘提纲

1. 需求：自然语言订单比较，正确处理未知与空数据。
2. 实现：模型决策，程序校验、执行与反馈，按预算结束。
3. 评测：规则检查过程与答案，独立参考计算，注入边界。
4. 证据：说明具体任务与次数，不将不同阶段结果合并。
5. 取舍：固定任务可以用工作流；Agent用于学习动态选择，增加成本和不确定性。
6. 局限：开发集小、无生产验证、重试缺失，确定性计算是合理下一步。
